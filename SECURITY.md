# Security

The security design follows from three goals:

- No accounts required[^deploy]
- Untrusted host
- Usability

The basic security model uses a single passphrase, preferably generated by
the app. The rest of this assumes a secure passphrase.

The passphrase is expanded via 650K iterations of PBKDF2 and split into an ID
and encryption key. The plaintext is encrypted with AES-GCM and submitted to the
server along with the ID. The passphrase is persisted in localStorage and
overwritten when changed. No additional security is provided on passphrase
storage because it would add friction to user experience.

Links to a board can be shared via the app, and can include the passphrase. If
shared in a way other than the built-in QR code scanner, this can lead to
passphrases ending up in logs and history. Passphrase and salt are shared as
URL fragments[^fragment], and removed by the app on load.

The server never sees the encryption key and is therefore limited on what it
can do:

- Record metadata such as IP, request size, modification times, etc.
- Record previous messages for the same ID, and send them back out of order.
- Attempt to brute force the passphrase using the ID as an oracle. Assumed
  practically impossible for secure passphrases or unknown salt.
- **Serve a malicious client that steals the passphrase.**

A client that knows the server address could:

- DOS it by submitting many random boards, pushing out existing boards.
- Load & destroy ciphertext for a known ID. If it knows a valid ciphertext for
  the ID, it can resubmit it whenever.

## Additional Mitigations

In addition to the security model, there are some additional steps taken to
prevent abuse and discovery by third parties. If you only ever used the domain
yourself, and were rigorous in how you shared the links, this would add
security. In practice, these values are easy to leak, and must be shared with
all users of a deployment, so they don't add security. More for mitigation of
DOS by bots.

1. **Unique subdomain.** The server is deployed with a unique subdomain. This
   ensures localStorage is limited to the deployment, and is needed for
   Cloudflare Workers.
2. **Secret route in the path.** `subdomain.example.com/secret_path`. Any
   request without the path never reaches the API. Similar to link sharing a
   doc, but constant for the deployment. Since it's in the path, it gets
   encrypted with HTTPS, unlike the subdomain that can leak via DNS.
3. **Salt as URL fragment.** The salt is shared as a URL fragment and the
   server never sees it. Without knowing the salt, brute forcing weak
   passphrases is not practical. However, this isn't the job of a salt, and
   it's constant per deployment. The path secret[^path-rotate] and
   subdomain[^subdomain-rotate] can be rotated without affecting stored boards,
   but the salt cannot be rotated without making previous data inaccessible.
4. **Trivial free self-hosting.** This mitigates much of the risk of an
   untrusted host. See README.md for a guide on how to deploy. Only requires a
   free Cloudflare account.

[^deploy]: A free Cloudflare account is required for documented deployment.
[^fragment]: URL fragments (`#fragment`) do not get sent in a request.
[^path-rotate]: Clients need to be updated with new path.
[^subdomain-rotate]: A new subdomain is a new localStorage. Passphrases would
    need to be manually transferred.
